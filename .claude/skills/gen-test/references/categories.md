# Test Category Specs and Stub Templates

Six categories required in every test file generated by `gen-test`.
Categories 1–4 are scoped to the individual module. 5a is per-module numerical accuracy.
5b is a shared pipeline integration test that lives in its own file.

---

## Category 1 — Deterministic Baseline

Given synthetic input data with known, hand-calculated expected values, does the module
produce the exact expected output?

**Why this matters:** This is the foundation. If a module can't produce correct output from
known input, nothing downstream is trustworthy. No randomness, no fuzzy assertions. You
craft the input, you hand-calculate the expected output, you assert exact equality (or
equality within floating-point epsilon for numerical computations).

## Category 3 — Provenance Fields

Every row written to the database must carry the metadata fields required for
traceability: `session_id`, `participant_id`, `site_id`, `sponsor_id`, `created_at`,
config version references, and any table-specific provenance columns.

**Why this matters:** Every data point must be traceable to the session, the config that
produced it, and the time it was created. A row without `session_id` is an orphan. A row
without `arc_config_version` can't be compared across sessions. These fields are
non-negotiable on every write path.

## Category 4 — No Direct `audit_events` Writes

Batch modules must NOT write directly to the `audit_events` table. Audit trail entries
are produced by database triggers (`AFTER INSERT` / `AFTER UPDATE` on target tables).

**Why this matters:** If a module writes its own audit events, the audit trail can be
bypassed by any code path that forgets to call the audit function, and faked by any code
path that writes directly. Trigger-based auditing is tamper-resistant. Testing that the
module never writes to `audit_events` directly confirms the architectural boundary.

**Exception:** Some modules DO write directly to `audit_events` for named lifecycle events
(e.g. `arc_batch_complete`). These are explicit lifecycle events — not row-level audit
trails. Tests must distinguish:
- Row-level auditing → must come from triggers, module must NOT write these
- Lifecycle events → module DOES write these, test that they appear with correct `event_type`

## Category 5a — Component Convergence Accuracy

For modules in the `batch/arc/` package that perform signal extraction or convergence
computation, verify that the module's computational output lands within ≤6–8% of a
known ground-truth value computed from synthetic data.

**Why this matters:** If `baseline.py` computes RMSSD one way and `processor.py` computes
it a slightly different way, deviation scores compare apples to oranges and every ECP is
untrustworthy. This test catches per-component drift before it compounds through the pipeline.

**Applicability:** Only applies to modules that perform numerical computation on biosignal
data. If the module does not import from signal extraction or convergence modules, skip
this category with a comment explaining why.

## Category 5b — End-to-End Pipeline Convergence Accuracy

A single shared integration test that feeds synthetic multi-modal session data through
the entire post-session batch chain and asserts final ECP convergence densities land
within tolerance. **Lives in `tests/capture_tests/arc/test_convergence_e2e.py`, not in
the per-module file.**

**Why this matters:** Every individual module might pass its own accuracy check, but
accumulated rounding, filtering, or logic differences across the full chain can compound
into a meaningful deviation that no single component test would catch. Each module is
"right" in isolation but the pipeline output is wrong.

### When to Update the E2E Test

Update `tests/capture_tests/arc/test_convergence_e2e.py` whenever:
- A new module is added to the post-session batch chain
- The batch chain ordering changes
- A new signal modality is added
- The convergence computation functions change
- The shared extraction functions change

When `gen-test` is invoked for any `batch/arc/` module, always check whether the E2E
test needs a corresponding update and flag it to the user.
