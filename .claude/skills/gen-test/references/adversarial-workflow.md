# Adversarial Model Workflow

## The Problem

When the same model writes both production code and tests, there is a shared blind spot
risk. If the model misunderstands how RMSSD should handle an edge case, it writes the
implementation wrong AND writes a test that asserts the wrong behavior. The test passes,
you get green checkmarks, but the code is wrong. The test is "lying" because the same
reasoning error produced both sides. This is the same problem as a student grading their
own homework.

## The Rule

**The model that wrote the production code must NOT write the test assertions.**

The structural scaffolding (test class names, fixture setup, the six category stubs,
file naming) is safe to generate with any model — structure is model-agnostic.
The dangerous part is the specific assertions about what values should come out of
a given input. That is where adversarial separation is required.

## The Annotation Block

Every test class generated by `gen-test` must include this comment block:

```python
# ASSERTION SOURCE: spec-only
# Feed the function signature and relevant spec section
# to an adversarial model. Do NOT share implementation source.
# Model used for assertions: ___________
```

The `Model used for assertions` field is an audit trail. When a test fails six months
from now, you can check whether the assertion was adversarial or self-graded.

## The Workflow

1. **Identify which model wrote the production code.** If Claude Code wrote `baseline.py`,
   Claude Code must not write the assertions for `test_baseline.py`.

2. **Prepare the assertion brief.** Extract from the module:
   - Function signature (name, parameters, return type)
   - Docstring
   - The relevant spec section (e.g. phase-3b-baseline.md agent file)
   - The target table schema (column names, types, constraints)
   - Do NOT include the implementation source code.

3. **Send the brief to a different model.** Options in Jay's setup:
   - Qwen (local via Ollama) — good for straightforward numerical assertions
   - Codex — good for code-aware assertion generation
   - A different Claude instance with explicit instruction to NOT see the implementation
   - For ground truth values (Category 5a/5b): compute independently in a different
     language (e.g. R, Julia, or a numpy script written by a different model)

4. **Fill in the `Model used for assertions` field.** This is the audit trail.

5. **Third-model audit (optional but recommended for Category 5a/5b).** After both
   production code and tests exist, have a third model review the test against the
   implementation and flag anywhere the test appears to mirror the implementation logic
   rather than independently verify it. This is the "test auditor" — not an agent that
   writes tests, but one that checks whether the tests are actually adversarial.

## What Counts as "Adversarial"

- ✅ Different model entirely (Claude → Qwen)
- ✅ Same model family, different instance, implementation source withheld
- ✅ Hand-calculated ground truth values
- ✅ Published reference values from literature (e.g. known RMSSD for a standard R-R series)
- ❌ Same model, same session, "now write the tests for what you just wrote"
- ❌ Same model with implementation visible in context
- ❌ Copying assertion values from the implementation's output ("it produced 42.7, so assert 42.7")
